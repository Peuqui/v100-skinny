## Purpose

Since #1251 both KV allocators (vllm/v1/worker/gpu/attn_utils.py for the V2 runner, gpu_model_runner.py for V1) reshape every carrier with the backend shape for kv_cache_spec.layout_cache_dtype(cache_dtype). layout_cache_dtype returns the configured dtype only when the spec's kv_quant_mode matches it, otherwise the spelling of the spec's own mode, "auto" for KVQuantMode.NONE.

Five places build MLA specs with cache_dtype_str but without kv_quant_mode: MLAAttention.get_kv_cache_spec, DeepseekV4 compressed attention (vllm/models/deepseek_v4/attention.py), DeepseekV4SWACache (vllm/v1/attention/backends/mla/sparse_swa.py), SlidingWindowMLASpec.merge, and the sliding-window-to-full conversion in kv_cache_utils.py. Their packed fp8 pages therefore get the "auto" carrier shape:

- GLM-5.3-Flash with --kv-cache-dtype fp8_e4m3 (Glm5NextSM70SparseBackend): the page has 520-byte token rows, the "auto" shape has 512, and the boot fails in _reshape_kv_cache with "shape '[20736, 64, 512]' is invalid for input of size 690094080" (690094080 = 20736 x 64 x 520).
- DeepSeek-V4-Flash with --kv-cache-dtype fp8: the sliding-window cache stores 584-byte rows in a 576-aligned page (64 x 584 = 37376 bytes, padded to 37440). The 512-wide "auto" view still fits, so the reshape succeeds as a strided view, and the SM70 sparse decode logs "SM70 sparse decode: paged fallback because requires device-local packed FP8 cache with contiguous block bytes" and leaves its BMM path.

At every site cache_dtype_str is the configured cache dtype, so binding the codec gives these specs the carrier shape they had before #1251.

This PR binds the codec in one place: MLAAttentionSpec.__post_init__ and SlidingWindowMLASpec.__post_init__ derive kv_quant_mode from cache_dtype_str and raise ValueError when a caller passes a contradicting mode. A fix at the construction sites alone would still lose the mode in SlidingWindowMLASpec.merge. Specs without cache_dtype_str (the indexer caches, the DeepSeek-V4 compressor state, the QSA compressed key cache, HiddenStateCacheSpec) are unchanged, and the callers that already pass both (platforms/interface.py, MLAAttentionSpec.merge) pass a consistent pair.

The padding-aware copy_with_new_block_size of #1256 moves from KVCacheSpec to AttentionSpec. On KVCacheSpec it reads page_size_padded and real_page_size_bytes, which the base class does not declare (pre-commit run mypy-3.10 on main reports three attr-defined errors and one call-arg error at vllm/v1/kv_cache_interface.py:156-158), UniformTypeKVCacheSpecs has neither field, and a MambaSpec page does not grow with the block size; only attention specs have a padded page whose payload grows with it. The new tests call copy_with_new_block_size on the MLA specs.

Not a duplicate: I searched the open PRs for layout_cache_dtype, kv_quant_mode, MLAAttentionSpec, SlidingWindowMLASpec and fp8_ds_mla; the only hits are our own #1221 and #1222, which change none of these files or how MLA specs get their codec. #1255 (merged) added NVFP4 to layout_cache_dtype and does not touch the MLA construction sites.

AI assistance was used for this change. I reviewed every line and ran the tests and measurements below.
