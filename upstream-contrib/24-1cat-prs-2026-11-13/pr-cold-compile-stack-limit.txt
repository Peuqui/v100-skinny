[Bugfix][Core] Restore the device stack limit a cold-compile warm-up grew

Problem: determine_available_memory warms the compiled graphs up with a first profile run and measures the second, so a cold compile does not shrink the KV budget. One cost of the cold compile still leaked into it: autotuning launches heavily spilling candidate kernels, which grows the CUDA driver's per-thread stack limit, and the local memory reserved for it (stack size times every thread the device can hold) stays allocated after the tuning and is charged as non-torch memory. GLM-5.3-Flash PP5 over 2x Quadro RTX 8000 + 3x V100 with empty Triton/Inductor caches: the stack limit on the RTX 8000 stages went from 1024 to 10240 bytes (V100 stages: 1424), non_torch was 0.65 GiB instead of 0.02 GiB, KV memory on PP0 1.17 GiB instead of 1.80 GiB, and the boot failed the KV check for the 524,288-token context. The next boot with warm caches passed. torch.cuda.empty_cache() does not return this memory.

Change: right after the warm-up profile run, if the stack limit grew, synchronize and set it back to the value before the warm-up. Kernels the steady state needs grow it again during the measured profile run, where they are counted. CudaRTLibrary (vllm/distributed/device_communicators/cuda_wrapper.py) gains cudaDeviceGetLimit and cudaDeviceSetLimit, with the hip mapping.

First commit: the fake workers of tests/v1/worker/test_gpu_worker_memory_profile.py, test_gpu_worker_profile_failure.py and test_sm70_warmup_allocator.py lack get_kv_cache_spec (the first two also vllm_config), which determine_available_memory reads since the attention workspace is configured there; all 25 cases fail on main 119cae740. They now stub configure_attention_workspace and get_kv_cache_groups (these workers have no attention layers) and return an empty spec. The allocator test also takes the graph memory estimate from compilation_config.runtime instead of VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS and gives its snapshots torch_allocated_memory, both read by the budget now. The stack-limit fix is the second commit.

Not a duplicate: no open PR touches the stack limit or the warm-up of determine_available_memory (searched open PRs for stack limit, cudaDeviceSetLimit, determine_available_memory, cold compile).

Tests (pre-commit passes on all changed files, mypy-local included):

- test_gpu_worker_memory_profile.py::test_cold_compile_stack_growth_is_not_charged (new): a fake cold warm-up raises the limit to 10240; without the fix it stays 10240 (assert 10240 == 1024 fails), with it it is back at 1024 and non-torch memory stays below the reservation.
- V100 (CUDA_VISIBLE_DEVICES=3), this branch on main 156cdaf1b: test_cudart_stack_limit.py, test_gpu_worker_memory_profile.py, test_gpu_worker_profile_failure.py, test_sm70_warmup_allocator.py: 27 passed. On main 119cae740 the last three fail all 25 of their earlier cases.
- RTX 8000 (CUDA_VISIBLE_DEVICES=0), this branch: the same four files: 27 passed.

Our four production entries (DeepSeek-V4-Flash in two configurations, GLM-5.3-Flash, Qwen3.8-27B-FP8) were then switched to fresh, empty compile caches and passed their control boots with the KV cache pools of warm-cache boots (509,292 / 317,261 / 550,502 / 851,394 tokens); without this change the cold GLM boot had failed.
