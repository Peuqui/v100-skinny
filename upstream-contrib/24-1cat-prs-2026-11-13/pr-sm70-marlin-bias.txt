[Bugfix][SM70] Add the Marlin bias on the SM70 dense and MoE paths

Problem: csrc/quantization/marlin/sm70_marlin_dispatch.cu rejects every bias with TORCH_CHECK(!has_bias, "SM70 Marlin does not support bias. TODO: add epilogue bias fusion."), while the Marlin callers pass the layer bias to ops.marlin_gemm (mixed_precision/marlin.py for GPTQ/AWQ, marlin_utils_fp8.py, marlin_utils_fp4.py). A Marlin layer with a linear bias therefore fails at engine start wherever the SM70 Marlin build serves it: on V100, and on Turing with an sm_70-only build such as ours (CMakeLists.txt builds the SM70 Marlin only without 7.5 in the Marlin arch list). Example: tests/quantization/test_fp8.py::test_online_quantization (opt-125m, FP8 online quantization through Marlin) fails 4 of 4 cases on a V100. The MoE dispatch (csrc/moe/marlin_moe_wna16/sm70_marlin_moe_dispatch.cu) rejects every bias the same way ("SM70 Marlin MoE does not support bias."), while fused_marlin_moe passes the w13/w2 biases (permuted per expert with marlin_permute_bias in int_wna16.py and marlin_utils_fp4.py).

Change:
1. The SM70 kernels have no bias epilogue, so the dispatch adds the bias to the finished output. The callers permute the bias into Marlin's single-scale column order (marlin_permute_bias) and the SM70 kernels write logical columns, so the bias is unpermuted first. The kernel that already undoes the scale order (64 for grouped scales, 32 otherwise) becomes the helper sm70_unpermute_half, used for both. The format branches moved into a lambda so that every format returns through the bias step; the branches themselves are unchanged. The bias must have the output dtype.
2. Refactor, no functional change: both dispatchers carried the same inverse scale and zero-point permutations and the same unpermute kernel, line for line. They move with sm70_unpermute_half to csrc/quantization/marlin/sm70_marlin_metadata.cuh (internal linkage, since the dense dispatch is in _C and the MoE dispatch in _moe_C); the MoE scale adapter calls it instead of its own launch. The zero-point unpack kernels stay per file, their indexing differs.
3. MoE: upstream Marlin MoE adds the expert bias before the top-k weight scales the row, out = (A W + bias[e]) * w. The SM70 MoE kernels have no bias epilogue and already scale their output, so after the GEMM a small kernel adds bias[e] * w (w = 1 without mul_topk_weights) to every row the store epilogue wrote: inside the padded token count, a local expert (expert_ids >= 0, so rows of other expert-parallel ranks stay untouched) and a sorted id below size_m * top_k. It uses one fused multiply-add (__fmaf_rn) and then rounds to fp16. The bias is unpermuted per expert, must have the output dtype and one row per expert; the format branches moved into a lambda as in the dense dispatch.
4. New test tests/kernels/quantization/test_sm70_marlin_bias.py (skips without the SM70 Marlin build). It packs the weights the way the loader does (gptq_marlin_repack, awq_marlin_repack, marlin_quant_fp8_torch) and checks FP8 (group -1 and 128), uint4b8 (group 128 and -1) and uint4 with zero points (group 128) at m = 1, 16, 256: the output with the permuted bias equals the output without bias plus the bias in fp16, bitwise; the bias passed without the permutation does not; the result is within 0.04 relative error of the fp16 reference. A CUDA graph captured with the bias matches eager calls after three replays with new activations, so the unpermuted bias copy made inside the call stays valid across replays. For the MoE path the per-expert loader packing is stacked: FP8, uint4b8 and uint4 with zero points (group 128), m = 1, 16, 64, top-k 2 of 4 experts, with and without mul_topk_weights and with expert parallelism (experts 1 and 3 local). The output equals the output without bias plus bias[e] * w, computed exactly and rounded to fp32 and fp16 as the kernel does, bitwise; rows routed to other ranks' experts are unchanged; the unpermuted bias does not match; the result is within 0.04 relative error of (a W_e + bias_e) * w.

The bias is added after the GEMM, not inside the fp32 accumulation, so the result can differ from a fused epilogue by one fp16 rounding; the test pins that behaviour. Calls without a bias do the same work as before.

Why a new test instead of test_marlin_gemm_with_bias: tests/kernels/quantization/test_marlin_gemm.py packs uint4b8/uint4 weights with marlin_quantize/awq_marlin_quantize, which build the upstream Marlin layout in Python. The SM70 repack produces a different layout, so on a V100 that file fails 561 of 593 cases on main with or without this change; 528 of them are combinations the SM70 path rejects on purpose (bf16, int8 or fp8 activations, is_k_full=False, act_order). With the loader's packing the SM70 GEMM matches the fp16 reference (relative error 0.0000 for uint4b8 and uint8b128, group 128 and -1, m = 16). We will bring that file in line separately. tests/kernels/moe/test_moe.py packs its Marlin cases with marlin_quantize as well (on a V100, -k marlin: 232 failed, 29 passed on main and with this change); its two bias cases failed at the bias check on main and now fail like its other 72 numeric cases.

Not a duplicate: no open PR touches sm70_marlin_dispatch.cu or sm70_marlin_moe_dispatch.cu (checked the files of all open PRs) or the SM70 Marlin bias (searched open PRs for Marlin bias, marlin_gemm bias, bias epilogue, SM70 Marlin, sm70_marlin_dispatch). #1506 (ours, tests only) lists test_fp8.py as still failing because of this bug.
