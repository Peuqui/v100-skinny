Problem: Nvfp4SkinnySm70Experts groups the routing slots of a decode or verify step by expert (argsort, group start, cumsum, scatter_reduce, dtype casts) with about 19 small torch kernels per MoE layer, about 86 us per layer in decode. Each of them is a launch of a few microseconds that the GPU mostly spends waiting.

Change:
- New vllm/model_executor/layers/fused_moe/sm70/routing.py with group_routing(topk_ids). Up to 128 slots (one token times 8 experts up to a verify step of 16 tokens) one Triton program on a single warp replaces the torch chain: one sort key per slot, expert * BLOCK + slot (the keys are distinct, so sorting them is the stable sort by expert; the slot rides in the low bits), one tl.sort, the group starts found by comparing neighbours and a cumsum, and a scatter of the starts into the group rows. Padding lanes take the largest key. Above 128 slots group_routing falls back to group_routing_reference, the torch version, which defines the result. Both return the same int32 tensors perm, gids and goff.
- Nvfp4SkinnySm70Experts._apply_grouped calls group_routing instead of the inline torch code (skinny_sm70_moe.py, 27 lines changed). The tensors the following kernels read are unchanged.
- Triton program size is one warp: for at most 128 keys more warps only add shared-memory round trips.

Evidence:
- Outputs are bit-identical to the torch reference: test_sm70_group_routing.py (CUDA) and the Triton-interpreter CPU test below compare perm, gids and goff with torch.equal for random routings of the GLM-5.3-Flash (288 experts, top 8), DeepSeek-V4-Flash (256, top 6) and a 9-expert shape, heavy ties, all slots on one expert, all slots distinct, int64 ids, negative ids and the 128/129-slot limit.
- Kernel time inside a CUDA graph (200 launches per graph, GLM shape, 8 slots, lower is better): 13.4 us -> 2.1 us on V100 and 17.8 us -> 2.6 us on Quadro RTX 8000 (RECHECK: re-run on this branch with the micro-benchmark, and the bit-identity check it prints). The older pairwise kernel in the same benchmark is the previous version of this file; the torch chain it replaced was about 86 us per layer in decode (our earlier measurement, RECHECK).
- End to end: in our fork a bundle of this change, the router GEMM fix, the KDA glue kernels (separate PRs) and a merge of 1Cat main measured GLM-5.3-Flash decode (short prompts, 192 tokens, greedy) 41.99 -> 44.50 and 44.41 tok/s on PP5 over 3x V100 + 2x Quadro RTX 8000. That figure belongs to the bundle, not to this change alone. RECHECK: A/B of this change alone on this branch.
