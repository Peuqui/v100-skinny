[Refactor][SM70] Drop the local compile-safe capability copies now that #1498 covers them; fix the GDN split test stubs

Problem: before #1498, model code that ran inside a compiled graph could not call current_platform.is_device_capability, because Dynamo cannot trace the platform's cached capability query. Four modules worked around it with their own torch.compiler.assume_constant_result wrapper: _sm70_gated_norm_device_supported and _sm70_gemma_long_prefill_available in vllm/model_executor/kernels/norm/sm70.py, _sm70_device in vllm/models/qwen4_exp/nvidia/sm70_mtp_fc.py and _volta_device in vllm/models/qwen4_exp/nvidia/sm70_fp16_gemv.py (#1496). #1498 now makes the platform query itself return a trace-time constant while compiling, so these wrappers answer the same question the same way. Separately, tests/models/qwen4_exp/test_sm70_gdn_projection_split.py replaces is_device_capability with lambda _: ..., which takes no device_id; since #1496 the admission passes device_id, so 23 cases fail on main with TypeError: <lambda>() got an unexpected keyword argument 'device_id'.

Change:
1. test_sm70_gdn_projection_split.py: the stubs take the device_id and answer True only for capability 70, so a query for the wrong capability also fails the admission cases.
2. The four wrappers go; the call sites ask current_platform.is_device_capability(70, ...) directly, with the same device arguments as before. tests/config/test_sm70_dflash2_policy.py stubbed one of the removed wrappers and now stubs the platform query. No behaviour change.

We carried the same kind of helper in our fork (one shared wrapper for these call sites) and replaced it with the #1498 platform query after merging main 156cdaf1b; this PR is that change against main.

Not a duplicate: no open PR touches these wrappers or the GDN split test (searched open PRs for assume_constant_result, is_device_capability, _volta_device, gdn_projection_split).
