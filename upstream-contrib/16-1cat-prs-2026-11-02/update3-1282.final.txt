Update 2026-11-03 (wheel): one commit added, 294882b45 "docs(triton): where to get the sm7x Triton, and the setting's error names it". The sm7x Triton that this PR's setting needs now has a prebuilt wheel: release v3.6.0-sm7x.2adbae8bc2 of github.com/Peuqui/triton, https://github.com/Peuqui/triton/releases/tag/v3.6.0-sm7x.2adbae8bc2 (Triton 3.6.0 plus the 26 commits of branch sm7x-tensor-cores, CPython 3.12, Linux x86_64, SHA-256 7b11b73c51d9cd8c7f494c001785ab0c1d78edb0db994dbfb82224b86d909bf1). The new page docs/design/sm70_triton_tensor_cores.md says what the build changes, how to install it in place of triton 3.6.0, how to check the installed build (the package metadata, since triton.__version__ stays 3.6.0) and how to go back; the RuntimeError of use_triton_sm7x_tensor_cores names that page. If you prefer to host the wheel yourselves, the same file and checksum can be mirrored as they are.

Against the source builds of the branch that the runs below used, the wheel carries two fixes: 19567626db stages a dot operand fed by two loads in the loop once instead of twice (on sm_75 with num_stages 3 or 4 the second copy could run before the store of the new tile, and the dot read stale shared memory; found in the FLA KDA kernel chunk_kda_scaled_dot_kkt_fwd_kernel_intra_sub_inter of GLM-5.3), and 2adbae8bc2 keeps loops whose staged buffers exceed the shared memory per block pipelined in registers, as Triton 3.6 does. With the same Triton fp16 GEMM kernel, 4096 x 4096 x 4096 runs at 82.5 instead of 8.6 TFLOPS on a Tesla V100 and at 80.7 instead of 7.5 TFLOPS on a Quadro RTX 8000 compared with stock Triton 3.6.0 (cuBLAS 94.4 on both); the release notes list the other shapes, Triton's own tests and a GLM-5.3-Flash A/B of the wheel against an earlier source build.
