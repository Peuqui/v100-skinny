[Test][SM70] Long-attention rows reference, Flash-V100 prefill skips on Turing, cover copy_block_ids

Problem, three test gaps on current main (9b349e712), found while running the SM70/Turing test files on a Tesla V100 and a Quadro RTX 8000 (sm_70-only build, so the RTX runs the sm_70 kernels where they exist):
1. tests/kernels/attention/test_sm70_long_attention_rows.py fails on the V100 (10 failed, 65 passed): test_request_rows_graph_matches_independent_requests compares a CUDA graph over batch x width rows with per-request runs of batch 1 using torch.equal. Since 4392c5853 the grouped E4M3 kernel picks its number of KV splits from the batch size (private_grouped_e4m3_fp32_paged: panel_split_cap and l2_split_cap depend on panels = batch * kv heads; #1518 changed the caps again), so the fp32 partial sums are combined in a different order and the batched and single runs differ by one fp16 ulp in 0.05 to 0.2 percent of the elements. All outputs are finite; it is not a computation error.
2. On the RTX 8000, test_sm70_flash_v100_anchored_swa.py (5 cases) and test_sm70_flash_v100_compact_pages.py (6 cases) fail with "Kernel supports only Volta GPUs.": the flash_attn_v100 paged prefill kernel checks for compute capability 7.0 itself (TORCH_CHECK in flash-attention-v100/kernel/fused_mha_forward_paged.cu). Their neighbours (test_sm70_flash_v100_varlen_layout.py, test_sm70_flash_v100_paged_prefill_determinism.py) already skip below SM70; these two did not.
3. KVBlockZeroer.copy_block_ids in vllm/v1/worker/utils.py, which the partial prefix cache of hybrid models (#1297) uses to copy whole KV blocks across all cache segments, has no test. A wrong copy would give silently wrong states.

Change: tests only, three commits.
1. The long-attention references keep the batch shape of the graph run, so they get the same split count: an eager run over the whole batch, and each request replicated across the batch (its table row, query rows and lengths repeated). The comparison stays torch.equal for every padding state (live, padded_rows, padded_request, empty, restore), and the test does not copy the kernel's split formula. A copy of the test that changes one output element by one ulp after the replay, or swaps two table rows, fails in all 32 request_rows cases.
2. The anchored-window prefill tests and the compact sliding-page test skip when torch.cuda.get_device_capability() != (7, 0), as the kernel requires and as the neighbouring tests do. The anchored decode tests still run on Turing.
3. New tests/v1/worker/test_kv_block_copy.py (6 tests): the zeroer is built through init_meta (as tests/v1/worker/test_kv_block_zeroer.py does) for an attention layer (K and V segments, 128 int32 elements per page) and a Mamba state layer of 5000 int32 elements per page, larger than the 1024-element tile and not a multiple of it, so the last chunk is partial. It checks bit for bit that destinations equal their sources in every segment and that every other block, sources included, stays unchanged, for several pairs in one call (not ascending, source block 0, destination at the end of the pool) and a single pair; that an empty list changes nothing; that out-of-range ids are skipped as the kernel filters them; and that uninitialized metadata raises. A guard test checks the premise (three segments, page sizes 128/128/5000, the partial last chunk). Three mutants of _copy_kv_blocks_kernel (last segment not copied, last chunk not copied, destination shifted by one) each turn the three copying tests red. Overlapping pairs are not tested: the scheduler emits copies only into freshly allocated blocks (kv_cache_manager.py, _redirect_partial_hit and _materialize_snapshots), so a destination is never also a source or a second destination in one step.
