# Decode vs live KV depth (llama-benchy)

4x V100-SXM2-16GB, TP4, GMU 0.88, MNS 1, fp16 KV, decode partition pinned 256
unless stated. Measured with `llama-benchy --exact-tg` (min_tokens +
ignore_eos), so decode work is identical at every depth. `--max-model-len` is
FIXED within each sweep, so the MML tax is constant and cannot masquerade as
depth. Driver `scripts/ctx_depth_sweep.sh` / `scripts/ctx_nospec.sh`.

## MTP k=7, pinned vs unpinned (MML 196,608)

| depth | pinned P=256 | unpinned P=1024 |
|---:|---:|---:|
| 0 | 127.41 | 116.33 |
| 8,192 | 91.56 | 92.40 |
| 16,384 | 79.68 | 72.00 |
| 32,768 | 68.22 | 83.76 ±32.40 |
| 65,536 | 54.71 | 55.82 |
| 98,304 | 44.77 | 36.63 |
| 131,072 | 37.44 | 35.17 |

**The partition size is not the lever.** Both collapse ~3.4x; at the deep end
the pinned arm is equal or better (44.8 vs 36.6 at 98k, 37.4 vs 35.2 at 131k).
This RETIRES the open question of whether pinning 256 is harmful above 32k of
live context -- it is not, and a dynamic-P / bucketed-capture fix would buy
approximately nothing.

Same-session shallow profiler windows confirm the pin's original win and where
it lands: pinned `wall=24.89 G0G1=17.47` vs unpinned `wall=26.24 G0G1=18.74`
-- +1.35 ms/round, in verify.

## Speculation ON vs OFF (MML 98,304)

| context | MTP k=7 | MTP off | MTP benefit |
|---:|---:|---:|---:|
| ~0.5k | 127.41 | 86.34 | **1.48x** |
| ~65k | 54.71 | 65.46 | **0.84x (net loss)** |
| degradation | 2.33x | **1.32x** | |

Decomposition over 0 -> 65k:
  per-step cost      1.32x   (measured directly, speculation off)
  total MTP loss     2.33x
  residual           1.77x   = tokens committed per round falling with depth

**Acceptance decay is the dominant term.** That is ordinary speculative-decode
behaviour, not specific to this stack or to Volta.

The per-step 1.32x is real but modest: step time 11.58 -> 15.28 ms, a 3.70 ms
rise, of which 64,512 tokens of fp16 KV (16 KB/token/rank = 1.03 GiB/rank)
accounts for ~1.3 ms. ~2.4 ms/step unexplained.

## k=3 at 65k (single depth, pinned, MML 196,608)

| at ~65k context | tok/s |
|---|---:|
| **k=3** | **76.26 +/- 8.79** |
| speculation off | 65.46 +/- 0.02 |
| k=7 | 54.71 +/- 12.77 |

**Speculation is not a net loss at depth -- k=7 is.** k=3 beats no-speculation
by 16.5% and k=7 by 39%. An earlier version of this file and of the README
said "past ~65k, turning MTP off is faster". That was WRONG: it generalised
from k=7 to all speculation without measuring a shallower depth.

This arm ran ONE depth, so its spec counters are a true per-depth measurement:
705 accepted / 456 drafts = **1.55 tokens accepted per round at 65k, k=3**,
against k=7's 1.63 measured arm-wide across all depths (not depth-resolved,
so treat the comparison as indicative).

Implied round latency: 33.4 ms at k=3 vs 48.0 ms at k=7. The 4 extra drafter
steps cost 14.6 ms == ~3.65 ms/step, against **0.817 ms/step measured at
shallow depth** (results/depth_curve_ours_20260819.md). The drafter step is
~4.5x more expensive at 65k because it reads the whole KV cache every step.

So the depth story has TWO terms, not one:
  1. acceptance decays with depth (the dominant term at k=7), and
  2. each drafter step gets more expensive with depth,
and together they mean the optimal k FALLS as context grows. The fix is
depth-dependent k, not disabling speculation.

**Not located:** the k=3 break-even, and the optimal k at 98k/131k. Only 65k
was measured at k=3.

## Notes

- MTP costs KV capacity: the speculation-off boot got **329,169** KV tokens at
  MML 98,304 against **232,967** with MTP -- the drafter and its workspace are
  worth ~96k tokens of cache.
- Disabling MTP is NOT achieved by dropping `--speculative-config`: the
  launcher carries an unconditional
  `export VLLM_1CAT_ENABLE_SM70_MTP_DEFAULTS=1` which injects
  `num_spec_tokens=4`. `scripts/ctx_nospec.sh` generates a variant launcher
  with that line parameterised, and hard-fails if `speculative_config=None`
  does not appear in the boot log.
- `VLLM_SM70_MTP_DYNAMIC_DRAFT_VOCAB_DEFAULT=0` is required even with
  speculation off, or boot dies with "Dynamic GPU LRU currently requires an
  FP16 LM-head" -- ours is QPN2 from checkpoint codes.
- llama-benchy runs (pp, tg, depth) as ONE test config
  (`runner.py:227`, expected tokens = pp + depth), so a `tg` row under
  `pp64512` is decode at ~64.5k, not at depth 0.
