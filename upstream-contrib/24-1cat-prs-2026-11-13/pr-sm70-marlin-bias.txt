[Bugfix][SM70] Add the Marlin bias on the SM70 dense path

Problem: csrc/quantization/marlin/sm70_marlin_dispatch.cu rejects every bias with TORCH_CHECK(!has_bias, "SM70 Marlin does not support bias. TODO: add epilogue bias fusion."), while the Marlin callers pass the layer bias to ops.marlin_gemm (mixed_precision/marlin.py for GPTQ/AWQ, marlin_utils_fp8.py, marlin_utils_fp4.py). A Marlin layer with a linear bias therefore fails at engine start wherever the SM70 Marlin build serves it: on V100, and on Turing with an sm_70-only build such as ours (CMakeLists.txt builds the SM70 Marlin only without 7.5 in the Marlin arch list). Example: tests/quantization/test_fp8.py::test_online_quantization (opt-125m, FP8 online quantization through Marlin) fails 4 of 4 cases on a V100.

Change:
1. The SM70 kernels have no bias epilogue, so the dispatch adds the bias to the finished output. The callers permute the bias into Marlin's single-scale column order (marlin_permute_bias) and the SM70 kernels write logical columns, so the bias is unpermuted first. The kernel that already undoes the scale order (64 for grouped scales, 32 otherwise) becomes the helper sm70_unpermute_half, used for both. The format branches moved into a lambda so that every format returns through the bias step; the branches themselves are unchanged. The bias must have the output dtype.
2. New test tests/kernels/quantization/test_sm70_marlin_bias.py (skips without the SM70 Marlin build). It packs the weights the way the loader does (gptq_marlin_repack, awq_marlin_repack, marlin_quant_fp8_torch) and checks FP8 (group -1 and 128), uint4b8 (group 128 and -1) and uint4 with zero points (group 128) at m = 1, 16, 256: the output with the permuted bias equals the output without bias plus the bias in fp16, bitwise; the bias passed without the permutation does not; the result is within 0.04 relative error of the fp16 reference. A CUDA graph captured with the bias matches eager calls after three replays with new activations, so the unpermuted bias copy made inside the call stays valid across replays.

The bias is added in fp16 after the GEMM, not inside the fp32 accumulation, so the result can differ from a fused epilogue by one fp16 rounding; the test pins that behaviour. Calls without a bias do the same work as before. The MoE dispatch (csrc/moe/marlin_moe_wna16/sm70_marlin_moe_dispatch.cu) still rejects a bias; not changed here.

Why a new test instead of test_marlin_gemm_with_bias: tests/kernels/quantization/test_marlin_gemm.py packs uint4b8/uint4 weights with marlin_quantize/awq_marlin_quantize, which build the upstream Marlin layout in Python. The SM70 repack produces a different layout, so on a V100 that file fails 561 of 593 cases on main with or without this change; 528 of them are combinations the SM70 path rejects on purpose (bf16, int8 or fp8 activations, is_k_full=False, act_order). With the loader's packing the SM70 GEMM matches the fp16 reference (relative error 0.0000 for uint4b8 and uint8b128, group 128 and -1, m = 16). We will bring that file in line separately.

Not a duplicate: no open PR touches sm70_marlin_dispatch.cu (checked the files of all 80 open PRs) or the SM70 Marlin bias (searched open PRs for Marlin bias, marlin_gemm bias, bias epilogue, SM70 Marlin, sm70_marlin_dispatch). #1506 (ours, tests only) lists test_fp8.py as still failing because of this bug.

Tests (pre-commit ruff-check, ruff-format, clang-format and mypy pass on the changed files). The kernel runs come from our fork with this change; its sm70_marlin_dispatch.cu, marlin_utils.py, marlin_utils_fp8.py, marlin_utils_fp4.py, mixed_precision/marlin.py and the marlin_gemm wrapper are byte-identical to main cb97f379b plus this PR:
