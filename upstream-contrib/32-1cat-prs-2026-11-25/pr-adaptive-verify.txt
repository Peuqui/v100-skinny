[Feature][Spec Decode] Per-round verify length for DFlash drafters (kernel_config.adaptive_verify)

Based on 1Cat main 73da3445d; four commits (the KernelConfig field and resolver; the scheduler controllers; the tail graphs from one source; a test fix).

Problem: A DFlash drafter proposes a fixed block of num_speculative_tokens draft tokens and the target verifies all of them every round. How many of them pay off depends on the text. On GLM-5.3-Flash with the DFlash2 drafter (PP5, one request at a time, a block of 6, the verify length forced to n per boot), the tok/s (higher is better) for n = 1 / 3 / 4 / 6 were, with sampling at temperature 1.0 and min_p 0.1: prose 36.09 / 35.59 / 34.23 / 29.91, explanation 40.17 / 44.82 / 40.87 / 38.06, code 42.55 / 58.00 / 58.20 / 55.58, arithmetic 43.07 / 58.62 / 57.98 / 59.78; and with a greedy client after an 8,687-token prompt 41.92 / 52.42 / 61.58 / 55.03. Among the lengths tried (2 and 5 were not), the best is 1 for prose, 3 for explanations, 3 to 4 for code, 6 for arithmetic and 4 after the long prompt, so any single num_speculative_tokens is a compromise. 1Cat main already adapts the depth for MTP (the async adaptive EntMTP of #1570: acceptance bands, depth k in [2, k_max]); nothing does it for DFlash. In addition the target-verifier tail graphs for 1 + n rows were registered by two parallel mechanisms (the legacy SM70 DFlash2 tail option and the adaptive MTP tails), and, as the code reads, a verify round shorter than the block is padded to the full block unless one of them is on, so a shorter verify length would not save time (not measured separately: all calibration runs had the tails).

Change:
- vllm/config/kernel.py: new KernelConfig field adaptive_verify (AdaptiveVerifyConfig: enabled, min_tokens, initial_tokens, forced_tokens, ema_alpha, prior_conditional_acceptance, prior_weight, verify_cost_ratio, switch_margin). Default off. The longest verify length is num_speculative_tokens, the drafter's block; there is no separate upper bound, since the drafter drafts its whole block anyway. One resolver, resolve_adaptive_verify(speculative_config, kernel_config, num_spec_tokens), is the single source for the scheduler and the CUDA graph manager. It raises ValueError, instead of ignoring the setting, for inconsistent bounds, for adaptive_verify.enabled with a method other than dflash, with MTP (MTP keeps the speculative-sampling policy adaptive_mtp), with ngram_assist (lookup-augmented DFlash2 verifies proposals wider than the drafter's block), and for the throughput rule without verify_cost_ratio. VllmConfig raises for adaptive_verify.enabled when async scheduling is off, since only the async scheduler chooses a length per round (check_adaptive_verify_scheduling). The former public is_adaptive_mtp_enabled and adaptive_mtp_min_k are now private helpers of the resolver (nothing else in the tree calls them). The field is ignored in KernelConfig.compute_hash: it is a scheduler decision and graphs are captured per shape. verify_cost_ratio has no default: it is the round cost of the model on the GPUs at hand (fitted on GLM-5.3-Flash here: 0.119, see Evidence). The field is a KernelConfig field, like other opt-in runtime switches in KernelConfig (for example topology_all_reduce); it does not take part in sampling and is ignored in the compile hash, while MTP keeps its existing owner, the speculative sampling policy.
- vllm/v1/core/sched/adaptive_verify.py (new) and async_scheduler.py: the EntMTP gate moves into the resolver in vllm/config/kernel.py and the controller into adaptive_verify.py, where build_verify_controller is the one dispatch point that picks the rule from the resolved plan. Rule mtp_bands is 1Cat's controller unchanged (EMA, bands, hysteresis, instant ramp-up; a test replays a recording of its depth sequence taken on 1Cat main 2d218ab03). Rule throughput, for DFlash, chooses argmax_n E(n) / (t0 + c * n) from a per-position conditional acceptance estimate (EMA, prior, censoring of positions a round did not verify, a switch margin, and 1Cat's probe one position further after a fully accepted round); c / t0 is the configured verify_cost_ratio. Rule forced verifies a fixed length every round, for calibration. The drafter keeps its full block; only the number of draft tokens the scheduler plans for the next round of a request changes. As for MTP, the length is adapted only while exactly one request decodes; with a larger decode batch the full block is planned (tested). Without the V2 model runner the plan is dropped, so MTP's automatic mode stays fixed there as before; DFlash, the one method adaptive_verify admits, runs on the V2 runner only. Tests drive the scheduler's own initialization with and without the V2 runner. Three startup log lines change: "Adaptive MTP (EntMTP-Async) enabled: k in [..]" becomes "Adaptive verify length (mtp_bands) enabled: n in [k_min, k_max], first round k_max.", and both "Capturing adaptive MTP single-request query lengths" and the legacy "Capturing SM70 DFlash2 target tail query lengths %s." become "Capturing target tail query lengths %s."; #1570 quotes the old MTP lines as startup evidence.
- vllm/v1/worker/gpu/cudagraph_utils.py: tail_query_lens is now the single source of the target query lengths below the full block. It replaces the parallel _adaptive_mtp_tail_graphs mechanism and the two flag checks in the single-request admission; with adaptive_verify enabled the target verifier of a block drafter captures a FULL graph for every 1 + n rows (n = min_tokens .. k_max - 1), single request only. The legacy SM70 DFlash2 tail option (q8 target verifier, q1..q7) and adaptive MTP (q3..q(k_max)) produce the same lengths as before; the attention tail route stays on its own flag. The drafter's own graph manager keeps its trained block width.
- vllm/v1/core/sched/output.py: the comment of next_spec_steps now covers every verify-length rule.
- The model runner, the rejection sampler, the PP packets and the drafter are not changed by this branch.
- Relation to #1616 (merged 2026-11-25): its AsyncScheduler code selects Inkling 2 DSpark draft widths (method dspark and a draft config of model_type inkling2_dspark) from a batch-size table (VLLM_INKLING2_SM70_DSPARK_WIDTHS) and a per-request width, and its _add_dspark_width_graphs captures the matching shapes. This branch leaves that code and its priority in _select_adaptive_batch_k untouched. The two never apply together: for method dspark the resolver returns None unless adaptive_verify.enabled is set, and enabling it for any method but dflash raises. The Inkling 2 widths are specific to that model and its DSpark drafter and driven by environment variables; adaptive_verify is a KernelConfig field for DFlash drafters (measured on GLM-5.3-Flash).
