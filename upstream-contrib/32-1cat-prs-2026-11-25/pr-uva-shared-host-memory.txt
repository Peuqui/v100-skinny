[Memory] Pin UVA-offloaded tensors at their exact size and share embedding tables

Based on 1Cat main 73da3445d; one commit (built on SharedHostArena from our fork commit 1f17e135f and the offloader part of 33a070e99; the test file uses torch.accelerator.set_device_index because the check-torch-cuda-call hook rejects torch.cuda.set_device).

Problem: UVAOffloader pins every offloaded parameter with Tensor.pin_memory(). That goes through the caching host allocator, which rounds each request up to a power of two and locks all of it. GLM-5.3-Flash at PP5 offloads its 1.18 GiB embedding table on the first pipeline stage and the DFlash replica of the same table on the last stage. Each copy held 2.00 GiB of shared host memory, 4.0 GiB for two copies of one table.

Change (vllm/model_executor/offloader/uva.py, plus a small accessor in vllm/utils/shared_host.py):
- New _HostBuffer: pinned host memory of exactly the tensor size (rounded up to whole pages, so at most 4 KiB more), built on SharedHostArena (sealed memfd, mapping, address) and registered with cudaHostRegister (portable, mapped) by _HostBuffer itself, since SharedHostArena leaves CUDA registration to its consumer. The registration runs inside the arena's registration_guard: concurrent long-term pins of one shared region can fail with ENOMEM (the reason pin_mmap_region in vllm/v1/kv_offload/cpu/gpu_worker.py serializes them), and here the stages that map one embedding table register the same pages. UVAOffloader._pinned_host_copy uses it instead of pin_memory() when pinning is on and the platform is CUDA-alike; the non-pinned path and other platforms keep the old code. It uses torch.cuda.cudart() like pin_mmap_region does; ROCm is untested.
- Embedding tables are shared. Processes on one host that offload a VocabParallelEmbedding with the same qualified name, shape, dtype, TP rank and DP rank find each other through the default torch.distributed store (compare_set on a key that contains the host name). The first process creates the arena and publishes its pid, descriptor number and arena identity (size, device, inode) under that key; the others open /proc/<pid>/fd/<fd> and pass the published identity to SharedHostArena, which checks it and the size seals. Only the creator copies the initial values, so a process that attaches never overwrites a table that another process is already loading. Without an initialized torch.distributed group every buffer is private.
- SharedHostArena gets a fileno() accessor so the creator can publish its descriptor number; nothing else in shared_host.py changes.
- The memory goes away with the last process that maps it, so a killed engine leaves nothing behind in /dev/shm.
- No other parameter type is shared; the key is built only for VocabParallelEmbedding.
