## Purpose

The EAGLE/MTP draft KV at a block's last position depends on the token after the block, so every prefix hit drops the last matched block. On hybrid models the attention block is unified to the Mamba page, so that block is 800 tokens on Qwen3.8-27B and 1,616 on Qwen3.8-Flash-Next: a 23,527-token resend hit 22,400 instead of 23,200 tokens and recomputed 1,127.

This PR backports vllm-project/vllm#61589 in its revision of 2026-10-14: each block hash also covers the token after the block and is emitted once that token exists, and the trailing-block drop is gone. A block is reused only when its lookahead token matches, so a hit reads the same draft KV as a cold run. The block before the last sampled token is published when the request stops.

Upstream merged a revised version on 2026-10-26 (2fb320d830). Differences to the merged version:
- Hash layout: here the lookahead token is appended to the block's extra keys; upstream hashes the block together with its lookahead window. Hash values therefore differ from upstream vLLM, which matters for external consumers of KV cache events and for engines sharing a KV store (both must run the same setting).
- KV events: upstream adds lookahead_token_ids to BlockStored; here the token travels in the extra keys.
- Multi-module MTP: upstream hashes one lookahead token per module (num_prefill_lookahead_tokens); here lookahead hashes stay off for it and the drop remains.
- Streaming sessions: upstream truncates at the kept end and rebuilds the chain on readmission; here the reset truncates the hashes that covered the discarded token.
- Upstream publishes the pending block after every output; here at stop. 1Cat's async scheduler already publishes after each output, and the sync scheduler at the next allocation.
I kept the revision that was measured below; re-syncing to the merged design is a follow-up I can do if you prefer it.

Fitted to this tree:
- The coordinator keeps the annotated EAGLE groups but takes drop decisions from drop_eagle_group_ids, which is empty without the drop (DeepSeek-V4 groups are annotated independently of use_eagle).
- The retention backport's replay boundaries, the Mamba lookbehind and the scheduler's aligned chunk split follow the drop; the encoder shift and the P/D lookahead limit keep EAGLE semantics (use_eagle vs use_eagle_block_drop, as upstream).
- Enabled with prefix caching for use_eagle_kv_cache() methods (DFlash keeps its own exemption), not with a KV connector or multi-module MTP, and switchable off with speculative_config.disable_lookahead_block_hashes. Scheduler-side only; the compile hash is unchanged. cache_blocks counts only hashed blocks. The streaming-session reset also truncates block hashes that covered the discarded token.
- DSpark gets no lookahead hashes and keeps the last-block drop as on main: on DeepSeek-V4 lookahead hashes lowered its acceptance (edit 5.69 -> 5.66-5.67 tokens per round, also without a prefix hit) and gave no TTFT gain in four runs. The merged upstream version also gives DFlash and DSpark no lookahead hashes.

This PR needs the aligned Mamba replay boundaries of #1240 (merged), because without the drop the replay boundaries must be aligned.

Relation to #1265 (merged, backport of vllm#53388): that PR changes only vllm/config/speculative.py; with its disable_eagle_block_drop flag set, use_eagle_kv_cache() returns False, which here switches off both the lookahead hashes and the drop. With this PR merged as well, the flag therefore keeps the last page without a lookahead check, as in upstream vLLM. Both PRs add a field to SpeculativeConfig; the rebase onto main kept both.

Relation to #1260 (open): it adds an opt-in verified MTP prefill cache (additional_config verified_mtp_prefill_cache, V2 runner native MTP, prompt blocks only) with a separate next-token proof hash per block (vllm/v1/core/prefill_boundary.py) and a lookup without the drop. The goal is the same, the mechanism differs: this PR puts the next token into the block hash chain, is on by default with prefix caching, and also covers generated tokens. Both change kv_cache_coordinator.py, kv_cache_utils.py, block_pool.py, kv_cache_manager.py and the scheduler, so whichever lands second needs a rebase, and you may want only one of the two mechanisms. With this PR that condition is the coordinator's drop_eagle_group_ids (empty for MTP/EAGLE with lookahead, set for DSpark); this PR does not touch the offloading scheduler, and lookahead hashes stay off with a KV connector, so the two do not interact until a connector run enables both.
