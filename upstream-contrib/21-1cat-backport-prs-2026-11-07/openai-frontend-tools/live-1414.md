## Purpose

Backport of three upstream vLLM fixes for the OpenAI-compatible frontend and its tool parsers, one commit each, in the same form as the earlier backports #657 (vllm-project/vllm#44082) and #1406 (vllm-project/vllm#60472). main does not have them. They are the part of a larger set on our fork that main still lacks: vllm-project/vllm#46303, #40986, #43984, #55743 and #42752 are already on main through #1317, #1309, #1308 and #1314, so they are not part of this PR. All three changes are frontend code and do not depend on the GPU; the Qwen3.8-27B release profile (vllm/sm70_profiles/qwen38_27b_nvfp4_dflash2.json) runs the code paths they fix, with --enable-auto-tool-choice, the qwen3_coder tool parser and, since #1299, --enable-prompt-tokens-details.

1. vllm-project/vllm#61297 (69d00bc26, by Yoni Gozlan), "Accept whole-number floats for integer tool arguments in the response parser". coerce_to_schema_type (vllm/tool_parsers/utils.py) tried only int() for an "integer" argument, so a value written as "3.0" or "1e3" failed there and reached the final json.loads fallback as a float (3.0). JSON Schema counts whole numbers written as floats as integers. The qwen3_coder, deepseek_v4 (through the DSML base parser), seed_oss and minimax_m2 tool parsers call this helper for non-string arguments. Upstream fixes _coerce in vllm/parser/chat_parsing/response_parser.py, which this repository does not have, so the intent is ported to coerce_to_schema_type. The integer and number branches now share one helper, _parse_finite_number: int() first, so large integers stay exact as with #1308, then float(), inf and nan rejected as with #1309, whole values returned as int. An "integer" argument accepts only a whole result; "3.5" keeps the existing json.loads fallback (3.5) instead of upstream's raw string, because this function already falls back that way for every type. The "number" branch returns the same values as before. The tests follow the upstream cases with these semantics, plus a deepseek_v4 parser test for "3.0" in batch and streaming.

2. vllm-project/vllm#44383 (42ae5e7ac, by sasindharan), "Fix --enable-prompt-tokens-details omitting zero cached tokens". With --enable-prompt-tokens-details, prompt_tokens_details was only set when num_cached_tokens was truthy, so a prompt without a prefix-cache hit, for example the first turn of a conversation, omitted the field instead of reporting cached_tokens: 0. This affects chat, completion and disagg serving (vllm/entrypoints/openai/chat_completion/serving.py, vllm/entrypoints/openai/completion/serving.py, vllm/entrypoints/serve/disagg/serving.py). The patch applies unchanged. Upstream tests the disagg stream (CPU) and /v1/completions (GPU server); a chat-level test is added for the streaming path with include_usage and for the non-streaming path.

3. vllm-project/vllm#46091 (7f616c327, by Ben Browning), "[Parser] Fix empty tool block silently dropping subsequent content". In the qwen3_coder streaming parser (vllm/tool_parsers/qwen3coder_tool_parser.py), a <tool_call> block that closes without a <function= header (an empty <tool_call></tool_call>, or a malformed JSON body) left the state machine waiting for a header in that block forever. Everything after it was dropped from the stream, text and any further tool call; the non-streaming path keeps the text as content and still finds later calls. Upstream fixes its ParserEngine (a TOOL_PREAMBLE -> CONTENT transition on TOOL_END); this repository runs Qwen3CoderToolParser, so the intent is ported to its state machine. A closed block without a function header is skipped. Because current_tool_index is also the index of the emitted call, skipped blocks are counted separately (skipped_tool_blocks) and block lookups use current_tool_index plus that count, so a call after an empty block keeps index 0. Content after the skipped block is emitted, and the search for the next tool marker starts behind it. As upstream, the empty markup itself is not streamed as content. The change applies unchanged next to #1313 and #1312, which change the same parser for other cases. Beyond a literal port, the block handling of extract_tool_calls_streaming is its own method, _stream_current_tool_block, and the skip continues with the next block in the same call. Otherwise an empty block and the next call's header in one delta, followed by the rest of that call in a single delta (a call without parameters, or multi-token deltas under speculative decoding), lose the call, because an EOS delta without text does not drive the parser any further; a test covers exactly this split, with and without parameters, and its batch counterpart.
