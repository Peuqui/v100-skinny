[Perf][GLM-5.3] Fuse the KDA decode glue kernels: q/k/v/beta packing and the gated RMSNorm

Based on 1Cat main 73da3445d (which contains #1549); one commit.

Problem: In decode and speculative-verify steps the GLM-5.3 KDA layer (Glm5NextLinearAttention) runs a chain of small operators around the recurrent kernel. Before it, when more than one row is present, four .contiguous() copies of q, k, v and beta that fused_recurrent_kda makes of the strided conv output and beta. After it, the eager FusedRMSNormGated.forward_native chain of the output norm: 11 operators for the fp32 recurrent output, 12 for an fp16 input (an extra x.float()). With custom_ops at its default under Inductor ("none") FusedRMSNormGated is not enabled and this eager chain is what runs, also for a model that is not compiled (Glm5NextModel has no support_torch_compile decorator). GLM-5.3-Flash has 34 KDA layers, so every step pays this 34 times. The operator counts come from a dispatch hook on the CPU (each operator is one kernel on CUDA); they are not a CUDA profile.

Change:
- New vllm/model_executor/layers/fla/ops/kda_glue.py (next to kda.py; neither kernel is specific to one platform) with two Triton kernels.
- kda_pack_recurrent_inputs packs q, k, v (1, T, H, D) and beta (1, T, H) into contiguous buffers in one launch (a pure copy). Glm5NextLinearAttention._recurrent_inputs uses it for the spec and non-spec recurrent calls when more than one row is present (for a single row the views are already contiguous and are used as before). This applies without any switch; it was run on the V100 and the Quadro RTX 8000 only (see Evidence).
- kda_gated_rmsnorm replaces the forward_native chain in one launch for a sigmoid gate and rows of 128 values, with an fp32, fp16 or bf16 input, an fp16, fp32 or bf16 gate and a weight of one row (tested with the model's fp16 gate and weight). It follows torch's fp32 operation order: x*x stored before summing (enable_fp_fusion=False, no FMA contraction), four sequential values per lane then torch's halving tree over 32 lanes (lane i with lane i + 16, 8, 4, 2, 1), the exact mean scale 1/128, libdevice expf and a round-to-nearest division for the sigmoid, one rounding cast. For fp16 and bf16 the input is widened exactly as forward_native does with x.float() first. The output is bit-identical to forward_native in the tested cases (see Evidence). A program handles four rows with one contiguous load (the four values of a lane are separated with two tl.split, the order of the sums is unchanged) and uses two warps from 4096 rows (64 tokens of 64 heads) on, four below.
- The norm kernel is the body of FusedRMSNormGated.forward_cuda for the calls it covers: sigmoid activation, affine weight without bias, no residual, no prenorm, rows of 128 values, operands of one of the three dtypes with equal element counts (kda_gated_rmsnorm_supported). Every other call still goes to rms_norm_gated. out_dtype is handled as in forward_native (default: the dtype of x).
- The CustomOp keeps deciding whether forward_cuda runs: with +fused_rms_norm_gated in custom_ops, or when custom_ops contains "all" (compilation mode NONE, for example enforce_eager, or a backend other than inductor; vllm/config/vllm.py appends "all" there), where FusedRMSNormGated is on by default. The default under Inductor and an explicit -fused_rms_norm_gated keep forward_native. No platform default is added and enforce_enable is not used. Glm5NextLinearAttention keeps calling self.o_norm in both branches, as since #1165, so that dispatch stays with its owner.
- Where forward_cuda already runs on main (custom_ops "all"), the covered calls now take the fused kernel instead of rms_norm_gated. tests/kernels/core/test_fused_rms_norm_gated.py calls forward_cuda and passes on both GPUs (see Tests). The fused kernel returns a new tensor, while rms_norm_gated writes its result into x when out_dtype is None; all callers of FusedRMSNormGated in the tree (the GLM-5.3, Kimi and Bailing layers) use the returned value.
- Other users of FusedRMSNormGated with a sigmoid gate: kimi_gdn_linear_attn.py (line 225) and bailing_moe_v3.py (line 747) build it over head_dim. Wherever forward_cuda runs for them (custom_ops "all", which is the default with enforce_eager or a backend other than inductor, or +fused_rms_norm_gated), calls with rows of exactly 128 values now reach the fused kernel; the head sizes of those models were not checked here. For those calls the result changes from the rounding of rms_norm_gated to the rounding of forward_native, a bounded numeric change: tests/kernels/core/test_fused_rms_norm_gated.py compares forward_cuda with forward_native (compiled with torch.compile in the first two tests, eager in the fp32-input test) within its tolerances (atol 1e-3 and rtol 1e-2; atol 2e-3 for the fp32 input), including bf16 input with a sigmoid gate and 128-wide rows and an fp32 input with an fp16 gate and output, and passes on both GPUs. Under Inductor with the default custom_ops "none" nothing changes for them.
- Prefill, the chunked kernel and the PP/graph structure are untouched.

What applies on main with this change: the packing, on every CUDA device the Triton kernel runs on. The norm, for fp32, fp16 and bf16 input, once the op is enabled (for example --compilation-config '{"custom_ops": ["+fused_rms_norm_gated"]}'). Without it the norm stays on the eager forward_native chain. The fp32 recurrent-output route of the layer is limited to compute capability (7, 0) on main (_use_sm70_fp32_recurrent_output), so the fp32 input case concerns the V100; the fp16 input is what every other card, and every non-recurrent step, feeds the norm. Tested and measured only on sm_70 (Tesla V100) and sm_75 (Quadro RTX 8000) with torch 2.10.0+cu128 and Triton 3.6.0; the bit-identity follows torch's reduction order for these shapes and was checked with the model's fp16 gate and weight only (fp32 and bf16 gate and weight are admitted by kda_gated_rmsnorm_supported but not compared bit for bit). Other devices are untested.

Related kernels: the tree already has an exact gated RMSNorm for 128-wide rows with a sigmoid gate, sm70_rmsnorm_gated_exact (vllm/model_executor/kernels/norm/sm70.py, used by RMSNormGated in layernorm.py). It serves the class RMSNormGated, not FusedRMSNormGated, behind kernel_config.sm70_rmsnorm_gated_exact on compute capability (7, 0), and only for contiguous 2D fp16 input, gate and weight with at most 768 rows unless the native library reports another capacity; the KDA output norm takes a 4D fp32 input on the V100 route and runs on Turing too, so it does not fit here. Merged #928 removed the same kind of copies for the GDN MTP recurrence by reading row-strided q, k, v inside the recurrent kernel (fused_sigmoid_gating.py). Doing that in fused_recurrent_kda would remove the copies altogether; this change leaves the recurrent kernel untouched and packs in one launch instead, and the two approaches were not compared.
