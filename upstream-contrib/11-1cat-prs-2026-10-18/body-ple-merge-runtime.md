Title: [Bugfix][Qwen4Exp] Decide the PLE cascade merge when the layer is built
Branch: Peuqui:pr-ple-merge-runtime (c04e2da46 on main 6f3557c97; fork commits 6bbcd40be + 99ec940c8)

## Purpose

With the PLE disk cascade, which is on by default (KernelConfig.ple_disk_cascade) and admitted for FP16 Qwen4Exp models with FP8 or packed GGUF PLE storage on local multiprocessing workers, the n-gram embedding is computed without its resident rows. PleOffloadLayer.forward asks offload_keeps_local_tables() on every call whether to gather the layer's own rows and merge the offload worker's rows into them. For Qwen4ExpNGramEmbedding that answer is ple_cascade_configured() or pinned_decode_active(), and both read kernel_config from get_current_vllm_config_or_none(). The GPU worker makes the config current only around worker construction, init_device, initialize_from_config and load_model. Profiling, torch.compile tracing, warmup, CUDA graph capture and execute_model run without it (vllm/models/qwen4_exp/nvidia/model.py:1164 notes the same for capture), so every forward, eager or compiled, answers "no" and returns the offload worker's raw output buffer. The worker writes only the disk-tier slots of that buffer (_remote_lookup); every slot whose row is resident keeps what the buffer held: zeros from the dummy and capture runs, or rows left over from earlier chunks and requests.

The cascade reached main in #806 together with 41faaa6d1, which moved ple_cascade_configured() from VLLM_QWEN4EXP_PLE_DISK to the kernel config, so on main the merge has not run at runtime since the cascade exists. How much is affected depends on the placement and the prompt. On our PP4 entry (131,045,319 of 320,001,536 rows in device memory) it was 10,592 of the 25,856 n-gram slots in the first 1,616-token chunk of a German prompt (41 %). On TP2xPP2 (125,439,175 of 160,000,768 rows per rank in device memory) most rows are resident. From the source only, not run: when a placement leaves no rows on disk, the worker zeroes the whole buffer, so the n-gram embedding is all zeros. Because the stale rows depend on earlier requests, the same prompt got different log-probabilities on every pass within one boot.

The guarded constructor already decides once, while the config is current, whether the layer builds its resident tables. This PR records that decision in the instance and lets the forward use it, the same way Qwen4ExpNGramEmbedding already keeps _cascade and _pinned_decode from its constructor, and the way #1004 and #857 moved policy reads to layer construction. Not changed: the packed GGUF pinned path, whose forward returns through the _pinned_decode branch before this check; the hybrid policy, which the cascade admission excludes and for which the recorded value equals the old runtime answer; and Qwen4ExpNGramEmbedding.load_weights, which repeats the guard but runs inside load_model's config.

The new test builds a layer while its keeps-local-tables answer is true, then flips the answer as the missing runtime config does. Its forward_impl takes resident ids itself and the remaining ids from a worker buffer in which only the worker's slots are written; on main the forward returns that buffer and the resident slot comes back as 0.
