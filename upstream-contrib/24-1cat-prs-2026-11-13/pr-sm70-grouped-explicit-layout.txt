[Bugfix][SM70] Grouped e4m3 fp32 route: admit explicit groups again

Problem: tests/kernels/attention/test_sm70_flash_v100_prefix_decode_rows.py fails on a Tesla V100 on main (12 failed, 28 passed): every case of test_dflash2_e4m3_rows_take_grouped_fp32_and_match_prefill_route with two or more groups asserts the route prefill_prefix_decode_rows_e4m3_grouped_fp32, but the decode rows of the mixed prefill batch run on prefill_prefix_decode_rows_scalar. The outputs stay within the test's tolerance (largest difference to the prefill route 6.1e-5, tolerance 5e-3); the cost is speed.

Cause: 2742c8ed9 ("perf: share SM70 long-attention row tiles across request batches") added a request_query_layout check to grouped_fp32_reason in vllm/v1/attention/ops/sm70_grouped.py: for more than one group, runtime-packed request batches must carry their request boundaries in metadata.query_start_loc_cpu. grouped_e4m3_fp32_groups_allowed calls grouped_fp32_reason with layout="explicit_groups" and without metadata, so since that commit every explicit call with more than one group is declined with request_query_layout, and _run_mixed_rows_grouped_e4m3 (flash_v100/prefill.py) falls back to the scalar decoder. The explicit caller packs one table row per group of MIXED_ROWS_GROUP query rows itself; before 2742c8ed9 the check did not exist and the test passed (all 12 cases green at 2742c8ed9^ = 677e2df03).

Change: the request_query_layout check applies to the request_rows layout only (not explicit), as its comment describes. The request_rows path is unchanged.
