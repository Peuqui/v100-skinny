Title: [Bugfix][Worker] Reserve one block for the kpool tail ring during MRV2 warmup

Branch: Peuqui:pr-warmup-kpool-tail-block (base 1Cat main 022349e47, two commits: 8dfe489754 test alignment, 5369e14a43 fix)

----- Text -----

Problem: The MRV2 warmup (vllm/v1/worker/gpu/warmup.py, _reserved_block_count) sizes the GLM-5.x kpool tail (KpoolTailSpec) by tokens like a sliding window. The scheduler keeps one block per request for it (KpoolTailManager). The tail ring has kpool * next_pow2(cdiv(kpool + k, kpool)) slots; with kpool 4 that is 8 slots for num_speculative_tokens 1 to 4 and 16 for 5 to 12. With 8 slots, the 1024-token full-chunk warmup reserves a large number of tail blocks, hands out block ids beyond the end of the pool to the groups after it (Mamba and auxiliary groups), and their state reads and writes go past the end of the KV tensors.

Seen on GLM-5.3-Flash with DFlash2 on a 5-stage pipeline (3x V100 + 2x Quadro RTX 8000): with num_speculative_tokens 4 the pipeline stage PP3 died with an illegal memory access during warmup. The KV pool was 130 blocks on every stage in the boots that crashed. Replaying the warmup on the CPU with that stage layout, it hands out block ids up to 162 for that pool of 130 with 4 draft tokens; with 3 draft tokens up to 155 (for the pool of 131 that a later boot with 3 draft tokens had); with 5 and 7 draft tokens the ids stay inside the pool, which is why it went unnoticed. MTP with 3 draft tokens also has the 8-slot ring (in the replay also out of the pool; we did not boot 3 draft tokens without the fix).

Change (vllm/v1/worker/gpu/warmup.py):
- _reserved_block_count counts KpoolTailSpec as one block, like CircularBufferSpec (the scheduler holds one block for it).
- _warmup_cycle asserts that every block id it hands out lies inside the pool (kv_cache_config.num_blocks), so an oversized warmup batch fails at its source with a message instead of as a GPU fault on some pipeline stage.

Second commit (tests only, first in the branch): tests/v1/worker/test_gpu_warmup_blocks.py::test_kernel_prefill_warmup_runs_default_batch_and_extra_profile fails on main because the warmup gained a 16-token prefill cycle under speculation (#1562) and runs the smaller request-count cycles without prompt logprobs (#1557), without the test being updated. The expected token counts, the sample count and the prompt_logprobs expectations now follow the current warmup. Included because the test file of this fix is not green on main without it.
