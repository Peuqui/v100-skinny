Problem: Three things hold the skinny MoE decode of GLM-5.3-Flash below the cards' bandwidth.
- Projections whose scale rows span more than five bits stay on the compressed csf planes and are expanded to the scale raster on every call. On GLM-5.3-Flash these are nine projections of the last pipeline stage (layers 36 and 40 to 44; the widest row of each spans 33 to 56 above the row's smallest scale, where five bits carry 31). A profile of a decode round (nsys) shows nine launches of csf32_expand_kernel per round, only on that stage, 0.55 ms per round, and the raster path streams more bytes than packed planes.
- The Turing (m16n8k8) decode instance with five-bit planes takes 91 registers per thread and fits two 256-thread CTAs per SM (ncu), so fewer weight loads are in flight per SM than with the raster instance (80 registers, which fits three).
- The Volta (m8n8k4) decode loop (one row tile) fetched the codes of the next group only a part of a group ahead and drained the pipeline at every loop edge: ncu shows the DRAM stream at 63 to 67 % of peak, with long-scoreboard stalls dominating.

Change:
- vllm/model_executor/layers/quantization/utils/s5_scales.py: the plane format takes a width: SCALE_BITS = (5, 6), scale_bits_for(spread) returns the smallest width that carries a projection, encode_scales and decode_scales replace encode_s5 and decode_s5, PackedScales replaces S5Scales. Six bits add a second high-bit word per (tile, group), stored next to the first so a kernel reads both with one 64-bit load. The scale bytes the kernels decode are the raster's, so the result is bit-identical to the raster path.
- vllm/model_executor/layers/fused_moe/experts/skinny_sm70_moe.py: _csf_to_s5 becomes _csf_to_packed; each projection takes the smallest width that carries it, and only a projection no width carries (none on the GLM-5.3-Flash checkpoint of the runs below) keeps its csf planes. With all projections packed the shared raster of a card is freed as before.
- csrc/sm70_turbomind/ops/skinny_moe_qpn_sm70.cu, csrc/ops.h, csrc/torch_bindings.cpp: the width is a template argument of both skinny kernels (0 = raster, 5, 6), so the five-bit and raster instances keep their code; the op's optional tensor arguments are renamed s5_base/s5_nib/s5_hi -> packed_base/packed_nib/packed_hi (the v41sk copy of the op in the DeepSeek-V4.1 sources is a separate operator and unchanged). Main's schema of skinny_moe_qpn_sm70 has none of these arguments (#1286 adds them together with fragment_order), so against main the rename changes no existing name or signature; within the stack it renames what #1286 introduced. docs/contributing/1cat-development.md (Change a native binding, point 2) asks to preserve old custom-op names and signatures, so this is a deviation only for names that are not on main; a search of the tree finds no keyword use of either set of names, the six call sites (the layer, test_skinny_sm70_moe.py four times, test_skinny_moe_triton.py) pass the tensors positionally or leave them out.
- The m16n8k8 decode instance (one row tile, split-K 8) gets launch bounds of three CTAs per SM. Same arithmetic in the same order.
- The m8n8k4 decode path (one row tile) gets an explicit load ring of depth 1 for codes, scales and activation rows (kDecodeRing, like load_group in the m16n8k8 kernel), refilled right after a slot is read, and the same launch bound of three CTAs per SM for the split-K 8 instances. Math and summation order per group are unchanged.
- Registers per thread of the one-row-tile split-K 8 decode instances (cuobjdump -res-usage of the libraries built from #1286 and from this branch; STACK and LOCAL are 0 for each of these instances): Turing, raster / five-bit / six-bit / MXFP4: 80 / 91 / - / 77 before, 72 / 76 / 68 / 71 now. Volta: 126 / 77 / - / 76 before, 79 / 80 / 79 / 71 now. Elsewhere in the same library some skinny MoE instances have a stack frame (LOCAL is 0 in all of them): the Volta split-K 16 MXFP4 one-row-tile instance, which the ring also recompiles, has 64 registers and an 8-byte stack frame now (76 registers and no frame before); the Turing four-row-tile instances with five-bit and six-bit planes have 16 and 8 bytes (the five-bit one had 16 before). I did not measure the speed of the split-K 16 instance separately.
- tests: tests/kernels/quantization/test_s5_scales.py and tests/kernels/moe/test_skinny_sm70_moe.py cover both widths (round trips, plane shapes, the old five-bit bytes, refusal of too-wide rows, the width choice, the csf expansion against packed planes, and decode rows of the ring against the staged prefill path bit for bit, including warp slices of 1, 3 and 5 groups). benchmarks/kernels/benchmark_glm_skinny_moe_routing.py: seven real GLM-5.3-Flash layers per pipeline stage in one CUDA graph, routing drawn from measured expert histograms of five-row verify rounds, with a byte comparison of the outputs between builds.
Since the kernels are shared, other models that use the skinny MoE backend take the launch bounds and the ring as well.
